# Единое подключение Redis

**Ветка**: `infra/redis/shared-connection-v13`  
**Создано**: 2026-10-30  
**Статус**: согласовано

**Основание**: [общий план](../../ROADMAP.md#r18)

## Пользовательские сценарии и проверки

### US1 — Одно подключение приложения (P1)

Разработчик задаёт `Redis:Connection` один раз. Самостоятельный Redis, Data Protection
и пользовательские токены используют общий транспорт и выбранную базу.

1. Включённые Auth и Redis независимо от порядка регистрации используют одно подключение.
2. Auth с Redis работает без явного `AddRedis`; Auth без Redis не требует настроек и не создаёт соединения.
3. Разные приложения имеют независимые подключения; остановка одного не закрывает другое.
4. Изменение конфигурации после сборки приложения не переключает действующее подключение.

### US2 — Независимые настройки v12 и v13 (P1)

Администратор оставляет прежние поля для v12 и задаёт новый раздел для v13.

1. При наличии старых и новых значений v13 выбирает только новые.
2. Без нового раздела использующее Redis приложение отклоняет конфигурацию.
3. Старый способ чтения настроек не меняется от добавления неизвестного вложенного раздела.

### US3 — Сохранение данных и отказоустойчивых подключений (P1)

1. `Direct` поддерживает standalone и Cluster без отдельного признака Cluster.
2. `Sentinel` использует независимые реквизиты Sentinel и сервера данных, восстанавливает работу после смены primary.
3. Прежние защищённые данные и токены читаются с теми же ключами, базой и именем приложения.
4. Выбор базы сохраняется, включая ненулевую базу на поддерживающем её сервере.

## Функциональные требования

- **FR-001**: единственный раздел по умолчанию — `Redis:Connection`, поля `Mode` (`Direct` по умолчанию либо `Sentinel`), `Configuration` и `SentinelConfiguration`.
- **FR-002**: `Configuration` содержит штатные параметры клиента, включая адреса, пользователя, пароль и `defaultDatabase`; отдельного флага Cluster нет.
- **FR-003**: в `Sentinel` обязательны `serviceName` в `Configuration` и адреса в `SentinelConfiguration`. Реквизиты двух соединений не смешиваются. В `Direct` значение `SentinelConfiguration` игнорируется, а `serviceName` в `Configuration` запрещён, чтобы клиент не включил Sentinel неявно.
- **FR-004**: неизвестный режим, пустая/некорректная строка и неполный Sentinel отклоняются при настройке использующего Redis приложения; сообщения не раскрывают строки подключения.
- **FR-005**: старые `Redis:Host/Port/Db/...`, `Redis:ConnectionString` и `Auth.Redis*` не читаются и не служат резервными значениями.
- **FR-006**: все внутренние потребители используют одного владельца транспорта в контейнере приложения; владелец закрывает соединения данных и Sentinel. Между приложениями владелец не разделяется.
- **FR-007**: автоматическая регистрация нужна только при включённом Data Protection или Redis-хранилище токенов; ручной `AddRedis` остаётся доступен.
- **FR-008**: подключение фиксируется при построении приложения. Имена ключей, `ApplicationName`, срок Data Protection, назначение защиты токенов, JSON и логика аутентификации сохраняются.
- **FR-009**: документация RU/EN описывает новый контракт, несовместимые API и переход обновлением версии: новый общий раздел указывает на Cluster, прежние поля сохраняются для v12. Автоматического переноса состояния и обязательных переопределений для каждого приложения нет.

## Сущности и крайние случаи

Подключение — режим, параметры сервера данных и отдельные параметры Sentinel.
Существующие данные — ключи Data Protection и защищённые пользовательские токены.
Ненулевая база разрешена только там, где её поддерживает сервер; библиотека не переводит её молча в DB0.

## Критерии приёмки

- **SC-001**: все три внутренних потребителя используют выбранную базу одного подключения.
- **SC-002**: неверная новая конфигурация не вызывает незаметного обращения к старому серверу.
- **SC-003**: прежние защищённые данные читаются после изменения способа настройки; локальные проверки standalone, Sentinel и Cluster проходят.
- **SC-004**: остановка приложения освобождает транспорт и не влияет на другое приложение.

## Границы

Только Sitko.Core v13. Vault, production, приложения и соседние библиотеки не меняются.
Модульных переопределений, именованных подключений, горячего переключения и автоматического переноса данных нет.
Переезд данных между серверами требует отдельного согласованного переноса; сохранение формата не доказывает такой перенос.
