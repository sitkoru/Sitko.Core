# Аутентификация OIDC и JWT

## Пользовательские сценарии и проверки

### US1 — Вход в веб-приложение (P1)

Разработчик подключает совместимого поставщика OIDC без привязки к IdentityServer.
Пользователь проходит вход через поставщика и получает сессию приложения.

1. При обращении анонимного пользователя к защищённой странице приложение направляет его к поставщику с Code Flow и PKCE.
2. Корректный ответ после входа создаёт cookie; подменённое состояние или некорректный токен не создают сессию.
3. Настройка стандартных параметров OIDC позволяет задать callback и отображение claims, сохраняя обработку токенов модулем.
4. Приложение может завершить локальную сессию и запросить выход у поставщика отдельно.

### US2 — Доступ к API и пользовательские токены (P1)

API проверяет JWT, а серверное приложение получает пользовательский access token.

1. JWT с корректными подписью, issuer, audience и сроком принимается; недействительный отклоняется.
2. OIDC и JWT могут быть подключены совместно с явным выбором схемы в политике.
3. Без управления токенами возвращается сохранённый access token; с управлением истёкший токен обновляется через поставщика.
4. Хранилища в памяти и Redis сохраняют, возвращают и удаляют токены. Redis сохраняет совместимость существующих ключей и защищённых данных.
5. При выходе из cookie с включённым управлением токенами отзывается refresh token.

### US3 — Переход приложения на версию 13 (P2)

Разработчик использует инструкции на русском или английском для замены пакета, API и конфигурации.
Администратор Keycloak выдаёт роль клиента допущенным пользователям и запрещает вход остальным.

1. Инструкция перечисляет замены существующих публичных типов, регистраций и секций.
2. Переход с Google требует настройки ограничения клиента в Keycloak до открытия доступа.
3. Проверка ограничения охватывает новый вход, существующую SSO-сессию и внешнего поставщика.
4. Инструкция предупреждает, что отзыв роли сам по себе не удаляет существующую cookie приложения.

## Функциональные требования

- **FR-001**: пакет `Sitko.Core.Auth.OIDC` предоставляет `AddOidcAuth` и `AddJwtAuth`, сохраняя обе формы builder и параметры `optionsKey`.
- **FR-002**: секции по умолчанию — `Auth:OIDC:Client` и `Auth:OIDC:Jwt`; старые имена не поддерживаются автоматически.
- **FR-003**: схемы `Cookies`, `oidc`, `Bearer`, настройки аутентификации и прикладные политики сохраняются; `Sitko.Core.Identity` не изменяется.
- **FR-004**: стандартные обработчики ASP.NET Core выполняют протокол и проверку JWT; зависимость `IdentityServer4.AccessTokenValidation` отсутствует.
- **FR-005**: модуль использует актуальную совместимую стабильную версию Duende и поддерживает `None`, `InMemory`, `Redis` с прежними числовыми значениями.
- **FR-006**: получение/обновление/отзыв токенов и совместимость Redis/Data Protection проверяются на публичных границах.
- **FR-007**: настройка `OpenIdConnectOptions` не должна случайно заменять внутреннюю обработку сохранения токенов; отказ пользовательского обработчика не должен сохранять токены входа.
- **FR-008**: двуязычная инструкция описывает OIDC/JWT, переход с IdentityServer/Google, роль клиента Keycloak, Blazor и границы сессии.
- **FR-010**: Redis-хранилище токенов и Data Protection используют [единое подключение приложения](../20261030-090000-redis-connection/spec.md); плоские `Auth.Redis*` в v13 не читаются.
- **FR-009**: решение поддерживает только .NET 10; потребители, production и живой Keycloak в рамках реализации не меняются.

## Сущности и крайние случаи

Сессия приложения хранится в cookie; пользователь идентифицируется настроенным claim.
Набор токенов содержит access token, refresh token, срок и scopes. Отсутствующий токен
не равен успешной аутентификации. Отсутствующий идентификатор пользователя не допускает
обращения к общему ключу хранилища. Недоступность поставщика и отказ обновления токена
не должны интерпретироваться как успешное обновление.

## Критерии приёмки

- **SC-001**: сценарии US1/US2 подтверждены автоматическими проверками без живого Keycloak.
- **SC-002**: существующие проверки Redis/Data Protection проходят после миграции.
- **SC-003**: разработчик получает полную таблицу перехода и проверяемые примеры RU/EN.
- **SC-004**: приёмка реального Keycloak явно отделена от локальной проверки модуля и выполняется при отдельной миграции потребителей.

## Границы

Допуск административного клиента определяется в Keycloak по роли клиента. Модуль не
создаёт email-списки и не навязывает приложениям общую роль. Политики API остаются
ответственностью приложения. Многопровайдерность, самостоятельный протокол OIDC,
мгновенный отзыв cookie и изменение существующей модели хранения не входят в задачу.
