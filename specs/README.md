# Living-спецификации Sitko.Core

Spec Kit — основной процесс подготовки и выполнения изменений Sitko.Core. Агент сам
выбирает подходящие этапы по поручению и состоянию задачи; названия команд помнить
не требуется. Канонические правила выбора, переходов и остановок находятся в
[sitko-core-workflow](../.agents/skills/sitko-core-workflow/SKILL.md).

Полное поручение ведётся до проверенного MR. Исследование и проектирование
ограничиваются запрошенным результатом. Короткие объяснения, операции обслуживания
и редактура без изменения поведения не требуют отдельных материалов Spec Kit.
Прямые вызовы команд остаются доступны для выбора конкретного этапа.

`spec.md` — изменяемый актуальный контракт capability, а не снимок отдельной задачи.
Предыдущие состояния контракта сохраняются в Git и истории merge request. Формат
Spec Kit помогает работать с артефактами, но сами спецификации должны оставаться
понятными человеку и не зависеть от Codex, OpenCode, Pi, Superpowers или другой
обвязки.

## Перед началом изменения

Найдите пересекающиеся требования во всех `specs/**/spec.md`: ищите по терминам
предметной области, наблюдаемому поведению, producer, consumer и именам контрактов.
Определите каждую capability, поведение которой меняется.

- Если capability уже описана, обновите её canonical `spec.md`.
- Если затронуто несколько capability, обновите все соответствующие canonical specs.
- Создавайте новый каталог `specs/YYYYMMDD-HHMMSS-short-name/` только для самостоятельной
  capability, ещё не имеющей канонической спецификации, включая уже существующее
  поведение. Не создавайте отдельную capability ради внутреннего рефакторинга.
  Timestamp присваивается при создании и не меняется при следующих редакциях.
- Не создавайте competing spec для обхода merge conflict. Разрешайте конфликт
  содержательно в существующем контракте.
- Сохраняйте requirement ID, пока смысл требования не изменился.
- Внутренняя переработка без изменения наблюдаемого поведения не требует
  искусственной правки `spec.md`.

Для планирования выберите один основной каталог. Его `plan.md` и `tasks.md` могут
ссылаться на остальные затронутые спецификации. План, задачи, исследование
и временные чеклисты — рабочие материалы изменения. Они нужны для проектирования,
реализации и проверки, но не являются долгосрочным контрактом поведения.

## Завершение реализации

Перед слиянием завершённой реализации сохраните актуальный `spec.md` и файлы,
которые составляют его контракт, например схемы и описания протоколов. Рабочие
материалы удаляются после проверок и ревью в следующем порядке:

1. Завершите проверки полноты реализации и независимое ревью, которым нужны
   `plan.md`, `tasks.md`, исследование или чеклисты. Невыполненные требования
   нельзя скрыть удалением списка задач.
2. Перенесите сохраняющие значение сведения: требования — в `spec.md`, устройство
   и эксплуатацию — в обычную документацию, существенные обоснования решений —
   в подходящий долговечный документ. Отдельный ADR для каждого изменения
   не требуется. Результаты проверок и ограничения зафиксируйте в PR.
3. Удалите `plan.md`, `tasks.md`, `research.md`, временные чеклисты и другие
   материалы, нужные только для выполнения этого изменения. Название файла
   или его расположение не делают его временным: схемы и прочие части контракта
   сохраняются либо переносятся с обновлением ссылок.
4. Проверьте ссылки на удаляемые материалы и согласованность оставшихся
   спецификаций, документации и реализации. В PR укажите, где сохранены
   значимые решения и результаты проверок.

При squash-слиянии созданные и удалённые в одной ветке материалы не попадают
в историю основной ветки. Поэтому значимые сведения переносятся до удаления;
рассчитывать на сохранность рабочего плана только в истории ветки нельзя.

Очистка завершает реализацию, а не промежуточное исследование или проектирование.
При остановке незавершённой работы сохраните материалы для её возобновления.
Следующее изменение той же возможности обновляет существующий `spec.md`,
а план и задачи создаются заново в том же каталоге по актуальному контракту.

## Выбор существующего каталога

Поставленные скрипты Spec Kit выбирают каталог в таком порядке:

1. `SPECIFY_FEATURE_DIRECTORY` из окружения;
2. поле `feature_directory` в локальном `.specify/feature.json`;
3. ошибка, если ни один источник не задан.

Перед последующей правкой укажите существующий каталог, не создавая новую feature:

```bash
export SPECIFY_FEATURE_DIRECTORY='specs/20260827-120000-favorite-jobs'
```

В PowerShell используется тот же путь:

```powershell
$env:SPECIFY_FEATURE_DIRECTORY = 'specs/20260827-120000-favorite-jobs'
```

После этого запускайте нужную команду, например `$speckit-plan`. Файл
`.specify/feature.json` хранит локальное active-feature state и используется только
когда переменная окружения не задана. Собственный диспетчер каталогов не требуется.
