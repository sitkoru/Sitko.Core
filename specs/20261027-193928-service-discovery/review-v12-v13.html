InvoiceService

company.accounting.InvoiceService

Контракты различаются protobuf-пакетом. Тот же ключ используется для индивидуальных настроек.

Один порядок применения настроек

Общие значения задают политику приложения. Настройка конкретного контракта уточняет её, а явный код сохраняет возможность точечного переопределения.

  1. Значения SDK по умолчанию
  2. Общая конфигурация Default
  3. Общий callback в коде
  4. Конфигурация конкретного контракта
  5. Callback конкретного клиента или сервиса
Согласованное правило: каждый следующий уровень меняет только явно заданные значения. Индивидуальные настройки не копируют общий объект целиком.

Одинаковая модель применяется к клиенту и серверу. Повторные callbacks одного уровня выполняются по порядку; последнее явное присваивание свойства побеждает.

TLS и передача токена сохраняются

В Sitko.Core

Механизм общих настроек клиента и поставщик токена по умолчанию. Отдельный клиент может явно переопределить поставщика.

Учитываются клиенты из зависимых модулей; результат не зависит от порядка подключения общей политики и клиентов.

В MYCG.Core

Выбор пользовательского или системного токена остаётся в GrpcTokenProvider. Получение токена выполняется для вызова с учётом текущего контекста.

Входящая JWT/OIDC-аутентификация сервера подключается приложением отдельно.

Локально и в Kubernetes используем HTTPS / HTTP/2: обычные CallCredentials передаются по TLS. Текущая политика проверки сертификатов переносится в общие настройки MYCG и остаётся явной.

Сейчас одного IGrpcTokenProvider в DI недостаточно: v12 проверяет фабрику конкретного TClient. В v13 общая политика подключается через ConfigureGrpcClients(options => options.AddTokenAuth<TProvider>()).

Отличия от v12 · целевая схема v13

При отказе Consul допускаем ошибки обнаружения

Принятый простой вариант

Используем стандартный Microsoft DNS SRV. В проверенной версии 10.11.0 после исчерпания попыток DNS при тайм-ауте или SERVFAIL публикуется пустой список адресов.

На сохранение последних известных адресов не рассчитываем. Новый RPC может завершиться ошибкой.

Что должно управляться настройками

DNS-тайм-ауты, число попыток, обновления и задержки повторов. Отдельно — deadline RPC и политика его повторного выполнения.

Публикация восстанавливается после возвращения Consul; старт приложения не ждёт его бесконечно.

Балансировка переходит от gRPC к Microsoft SD

v12 Как работает сейчас

LoadBalancingPolicy выбирает встроенную стратегию grpc-dotnet: None, RoundRobin или PickFirst.

Стратегия работает вместе с собственным резолвером Sitko.Core.

v13 Целевая схема

Microsoft SD выбирает адрес перед отправкой запроса. Для новой схемы используем его штатный RoundRobin.

Встроенный балансировщик grpc-dotnet в этом пути отключён; прежнее поле нельзя просто перенести без изменения смысла.

Прямой Address задаёт один адрес. Для SD старые настройки None / PickFirst требуют явного решения при миграции; их эквивалентность новой схеме не обещается.

Другую стратегию выбора можно обсудить при подтверждённой потребности. Реализация своего балансировщика в этот переход не входит.

Отличия от v12 · целевая схема v13

Почему выбрана именно такая граница

Оставляем

  • SD как необязательную самостоятельную возможность.
  • Общий слой поверх Microsoft SD и отдельный провайдер Consul.
  • gRPC API, пригодный и для SD, и для прямых адресов.

Не вводим в эту переработку

  • SD в базовом App и фиктивный провайдер «на всякий случай».
  • Отдельный Consul-модуль без других потребителей.
  • Новый общий каталог подключений для Kafka, Redis и Consul.
Consul-специфика остаётся за границей gRPC. Это позволяет добавить другой провайдер позднее, не строя сейчас дополнительный фреймворк абстракций.
