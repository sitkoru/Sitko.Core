# План: обнаружение gRPC-сервисов

**Ветка Git**: `infra/service-discovery/microsoft-consul` | **Дата**: 2026-10-27 | **Спецификация**: [spec.md](spec.md)

## Краткое решение

Клиентская регистрация сохраняет `AddGrpcClient<TClient>()`, поставщиков токенов и метаданных. Типизированный клиент получает логический HTTPS-адрес, штатный обработчик Microsoft SD выбирает адрес из Consul DNS SRV, `SocketsHttpHandler` переиспользует HTTP/2-соединения. Собственный `sd:///` resolver, глобальное чтение каталога, подписки и старый Base64-формат удаляются. Смешанный переход не поддерживается.

Каждый полный protobuf-контракт публикуется отдельно. Имя для Consul DNS одинаково вычисляется клиентом и сервером из окружения и точного имени контракта. После привязки именованного слушателя публикуются доступный адрес и фактический порт; подтверждением жизни остаётся TTL.

## Технический контекст

- Язык и платформы: C#, `net8.0;net10.0`, SDK из `global.json`.
- Зависимости: Microsoft.Extensions.ServiceDiscovery и `.Dns` 10.11.0; текущий grpc-dotnet 2.80.0 первоначально сохраняется. Прототип с 2.84.0 не доказывает необходимости обновления пакета.
- Хранение: только штатные регистрации Consul и их TTL, без нового хранилища или собственного каталога контрактов.
- Платформы выполнения: локальные процессы macOS/Windows; Linux/Kubernetes. Доступный Pod IP задаётся общей конфигурацией существующего порта; манифесты в этой работе не меняются.
- Проверка: xUnit v3; настоящий TLS Kestrel и изолированный Consul-контейнер после подтверждения границ пользователем. Тесты на одной ОС не объявляются проверкой остальных.
- Производительность: прямой путь полезной нагрузки без прокси и новых полных буферов; ответ 256 МиБ и сравнительные измерения с прямым клиентом. Произвольный допустимый процент регрессии не назначается.
- Ограничения: не менять MYCG.Core, Vault, production и чужие стенды; не добавлять свой Microsoft SD provider, совместимость старой схемы, новый service mesh или повтор бизнес-RPC ради обнаружения.

## Constitution Check

1. **Факты и требования**: решения DNS SRV, TLS, полного имени и отсутствия совместимости подтверждены пользователем. Исходники и ограничения приведены в [research.md](research.md).
2. **Простой интерфейс**: клиенту достаточно существующей регистрации типа; общую настройку Consul выполняет один фасад `AddConsulServiceDiscovery(...)`. Для обычного клиентского хоста регистрация сервера не включается.
3. **Минимальное достаточное решение**: текущие точки — `GrpcClientModule.ConfigureServices`, `GrpcClientModuleOptions.ConfigureClient`, `AppWebConfigurationModule.ConfigureWebHost`, `IApplicationContext.GetModuleInstance<T>()`, регистрация/TTL в `ServiceDiscoveryManager`. Сохраняются подходящие фабрики и настройка TLS. Замены только grpc resolver недостаточно: старый каталог хранит контракты в собственном формате и не является SRV-каталогом контрактов; настроенный нулевой порт также не отражает адрес готового сервера. Невыполненными остались бы FR-002/003/005/007/014.
4. **Совместимость явно**: удаление публичных resolver API, изменение формата Consul и секций конфигурации описаны в [contracts/module-api.md](contracts/module-api.md). MYCG.Core должен перейти отдельно; его статические адреса не зависят от формата Consul.
5. **Наблюдаемый результат**: [quickstart.md](quickstart.md) задаёт предлагаемые публичные границы и конкретные данные. До их подтверждения тесты не пишутся и контейнеры не запускаются.
6. **Living spec**: один актуальный контракт в `spec.md`; исследование и план сохраняются до завершения реализации. Очистка — по `specs/README.md`, после ревью и проверок.

Новый универсальный реестр портов не нужен. `AppWebConfigurationModule` уже создаёт конкретный `ListenOptions` и доступен через существующий контекст. Сохранение ссылки на объект слушателя в самом модуле — минимальное расширение, необходимое для FR-005: при `Port=0` список адресов сервера теряет имя исходного порта.

Отдельная Consul-fixture нужна для FR-007/009/010: нынешний SD-тест обращается к общему `localhost:8500` и не проверяет перезапуск. Имеющаяся инфраструктура Testcontainers переиспользуется; общий стенд не меняется. Веб-серверы проверяются настоящими Kestrel, подмена сети не доказывает DNS SRV/TLS.

После проектирования нарушений принципов не выявлено. Условие начала тестовой реализации: подтверждены границы из `quickstart.md`.

## Структура проекта

Рабочие материалы находятся в этом каталоге: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/module-api.md`, `contracts/consul-registration.md`, `quickstart.md`, `tasks.md`, `checklists/requirements.md`.

Изменяемые области:

- `src/Sitko.Core.Grpc/GrpcHelper.cs` — отдельные helper полного protobuf-имени для нового SD. Существующие helper короткого имени сохраняют семантику: MYCG.Core использует их для ключей статических адресов; изменение этого поведения не нужно для нового SD.
- `src/Sitko.Core.ServiceDiscovery/` — общие объявления сервисов и DNS-имён; удаление собственных resolver/subscription API.
- `src/Sitko.Core.ServiceDiscovery.Resolver.Consul/` — модуль настройки штатного DNS SRV вместо своего resolver; существующий пакет переиспользуется.
- `src/Sitko.Core.ServiceDiscovery.Server.Consul/` — фасад общей регистрации и включение регистратора для существующего `ISitkoCoreWebApplicationBuilder`; сохраняются существующие пакетные границы без нового проекта.
- `src/Sitko.Core.ServiceDiscovery.Server/` и `src/Sitko.Core.App.Web/AppWebConfigurationModule.cs` — фактический именованный слушатель после bind.
- `src/Sitko.Core.Consul/ServiceDiscovery/ServiceDiscoveryManager.cs` — только регистрация, TTL и удаление; каталог и прежний сериализованный формат удаляются.
- `src/Sitko.Core.Grpc.Client/` — стандартный HTTPS-адрес и `.AddServiceDiscovery()` на существующем `IHttpClientBuilder`; токены/metadata/channel options сохраняются.
- `src/Sitko.Core.Grpc.Server/` — объявления полных контрактов и выбранного именованного порта.
- `tests/Sitko.Core.Grpc.Client.Tests/` — проверки через публичную регистрацию, TLS RPC и собственную fixture; `.proto` генерируются существующим способом.
- `apps/gRPC/` — актуальный пример потребителя; `.sln` и ссылки проектов обновляются только при фактической необходимости.
- `docs/` и ближайшая навигация — описание настройки, ограничений и действий потребителей.

## Этапы реализации

1. Согласовать публичные границы проверок; сохранить исходные диагностики затрагиваемых C#-файлов.
2. Вертикально реализовать полную идентичность и разделение окружений через публичные точки регистрации. Один падающий тест, минимальный код, успешный тест; далее следующий сценарий.
3. Подключить стандартный Microsoft HTTP/DNS путь и первую отдельную регистрацию Consul через тот же цикл TDD.
4. Обеспечить фактический TLS-порт, TTL, остановку, повтор регистрации и восстановление прежнего клиента после смены порта. Один владелец цикла регистрации/heartbeat/удаления; параллельные циклы и дополнительные блокировки без необходимости не вводятся.
5. Подключить конфигурацию к штатным опциям DNS; проверить отсутствие утечки токена и сохранение TLS. Время ожидания DNS и интервалы повторов не смешиваются с политикой повторов бизнес-RPC.
6. Проверить большой ответ, пример, совместимость сборки целевых проектов и диагностики; выполнить независимое ревью, `speckit-converge`, подготовить PR.

## Исполнение и фиксация результата

Обычные законченные группы реализации поручаются Sol 6.1 / medium по `task-delegation`; root интегрирует и проверяет. Группы с общей регистрацией выполняются последовательно. Проверку соответствия требованиям выполняет свежий рецензент. Планирование согласованных взаимосвязанных требований ведёт root Sol 6.1 / xhigh.

Документы подготовки можно фиксировать отдельным согласованным коммитом `docs(service-discovery): ... [skip ci]`. Дальнейшие коммиты — проверенные вертикальные результаты: идентичность; клиент+регистрация+фактические порты; восстановление/настройка; документация и итоговые проверки при необходимости. Падающий тест не фиксируется без работающей реализации.

## Необходимая инфраструктурная граница

Используется только собственный локальный Consul-контейнер с уникальным именем и случайно опубликованными loopback-портами HTTP и DNS. DNS требует учёта UDP/TCP; не предполагается, что оба протокола случайно получили один номер. Все адреса передаются тестовым хостам явно. Тест не обращается к `localhost:8500`, не запускает kind и не меняет общие настройки Docker. Удаляется только контейнер, созданный этой fixture.
