# Публичная регистрация и настройка

Это целевой контракт перехода; код на момент подготовки ещё не реализован.

## Потребитель

- `AddGrpcClient<TClient>()` сохраняется как точка регистрации клиента. Адрес извлекается автоматически из полного protobuf-контракта и общей настройки окружения.
- `AddGrpcServer(... RegisterService<TService>() ...)` объявляет обслуживаемые контракты. Отдельных списков для Consul не требуется.
- Общий фасад `AddConsulServiceDiscovery(...)` настраивает Consul DNS SRV и включает серверную регистрацию только для существующего веб-builder. Обычный клиентский host не требует `IServer`.
- Прямые внешние клиенты `AddExternalGrpcClient` и gRPC-Web не обязаны проходить через Consul; их назначение сохраняется.
- Токены, метаданные, интерцепторы и настройки размеров сообщений остаются доступными через существующие gRPC options.

## Конфигурация

Общая конфигурация находится в секции модуля `ServiceDiscovery:Consul`; подключение к Consul HTTP сохраняет общую секцию `Consul` и существующий `ConsulUri`. Дублирующие источники одного значения не вводятся.

Модуль предоставляет DNS servers/port, timeout per attempt, max attempts, default refresh period, min/max retry period и retry backoff factor. Серверная часть предоставляет TTL, heartbeat, deregister delay, registration request timeout и retry interval. Названия полей и значения по умолчанию фиксируются вместе с реализацией и соответствующим примером; простые числовые значения и TimeSpan должны привязываться обычной .NET configuration.

Инварианты: интервалы и число попыток положительны, heartbeat меньше TTL, максимальная задержка повтора не меньше начальной, адрес объявления не wildcard и фактический порт положителен. Применение всех параметров после перезапуска достаточно; горячее применение всех параметров не обещается.

Адрес/порт слушателя остаётся в существующей конфигурации `Application:Web:Ports`. Для Kubernetes доступный адрес передаётся общей настройкой `ExternalAddress` выбранного gRPC-порта. Фиксированные номера портов поддерживаются вместе с динамическим `0`.

## Несовместимые изменения и переход

- Удаляются `IServiceDiscoveryResolver`, `BaseServiceDiscoveryResolver`, `ServiceDiscoveryResolverFactory`, собственный `sd:///` и generic-регистрация registrar/resolver.
- Новый SD использует отдельные helper полного protobuf-имени. Существующие helper короткого имени сохраняют семантику для внешних потребителей, включая ключи статических адресов MYCG.Core; поддержка старой схемы обнаружения из этого не следует. Ключи индивидуальных настроек нового SD-клиента следует привязывать к полному контракту, чтобы одноимённые клиенты не смешивали параметры.
- Старые Consul-регистрации приложения/порта и их Base64-метаданные новой схемой не читаются. Двойная публикация не нужна.
- Пример Sitko.Core и его тесты переходят в этой ветке. MYCG.Core должен отдельно заменить общую регистрацию SD; при переходе на обнаружение удалить соответствующие статические адреса. Этот репозиторий и production сейчас не меняются.
- Политика повторов бизнес-RPC не расширяется вследствие миграции SD. Наблюдаемые ошибки и восстановление следующих вызовов описываются отдельно от повторного выполнения операции.
